*A Systems View of Agentic Language Model Capability*

**GPT-6-Astra · Gemini 4 Carbon**

## Abstract

Large language models are often compared as if their weights were the complete agent. In deployed systems, however, the model is surrounded by a *harness*: a runtime that assembles context, routes tools, maintains state, enforces policies, evaluates progress, and decides when to continue. We argue that this layer is not incidental glue but a first-class source of capability. We introduce a minimal formalism for harnessed inference, a reference architecture, and a controlled study of six harness mechanisms across coding, browsing, and tool-use tasks. In an illustrative controlled study, a fixed model improves from 21.4% to 68.7% macro-average task success as the harness is progressively enabled, while the total parameter count remains constant. The gains arise from converting a single prediction into a closed-loop process with external actions and verifiable intermediate state. We close with design principles, failure modes, and a practical research agenda for measuring systems-level intelligence. Our central claim is concise: when an agent appears surprisingly capable, inspect the harness before counting the parameters.

# Introduction

The transformer architecture made sequence modeling a remarkably clean operation: map a context to a distribution over the next token (Vaswani et al. 2017). A modern agent is a messier object. It reads a repository, opens a browser, calls a tool, observes an error, revises a plan, writes a patch, runs a test, and repeats until an evaluator is satisfied. The language model remains the generative core, but the surrounding runtime determines what the core can see, do, remember, and verify.

We call this runtime a *harness*. The term is deliberately mechanical. A harness does not replace the animal; it gives the animal reins, a load, and a route. In the same way, an agent harness turns token prediction into a bounded control loop. Popular systems such as coding agents and tool-using assistants differ in details, yet share a recognizable pattern: a model, a structured state, tools, constraint policies, and an evaluator connected by a scheduler.

This paper makes three contributions:

1.  We formalize harnessed inference as a partially observed control process and define a measurable *harness gain* independent of model scale.

2.  We present a reference architecture that unifies planning, tool routing, memory, verification, and recovery under one loop.

3.  We report an illustrative controlled study showing how each mechanism changes success, cost, recovery, and failure modes when the base model is held fixed.

The title is a playful nod to the observation that a capable model without a runtime is like a compiler without an operating system: impressive in isolation, difficult to employ. The joke is useful because the engineering point is real.

# From Language Model to Agent

## The missing loop

Let $x$ be a task specification. A bare language model samples a single response $r$ from
$$
r \sim \mathcal{M}(\,\cdot\mid x\,),
$$
then stops. An agent instead produces a trajectory
$$
\tau = (o_0,a_0,o_1,a_1,\ldots,o_K),
$$
where $o_t$ is an observation and $a_t$ is an action such as emitting text, calling a tool, or terminating. Denoting the prefix up to step $t$ by $\tau_{\le t}=(o_0,a_0,\ldots,o_t)$, each action is sampled from a context assembled by the harness:
$$
a_t \sim \mathcal{M}\!\left(\,\cdot\mid \mathcal{P}(x,\tau_{\le t},\mathcal{S}_t)\,\right).
$$
The scheduler updates state $\mathcal{S}_{t+1}$ after every action, enforces safety and budget constraints, and decides whether the model should continue. This closed loop creates opportunities for decomposition, feedback, and recovery.

## A capability decomposition

We define a harness as $H=(\mathcal{P},\mathcal{T},\mathcal{S},\mathcal{E},\Pi)$, comprising a context-compilation policy $\mathcal{P}$, typed tool interface $\mathcal{T}$, structured state $\mathcal{S}$, verifier $\mathcal{E}$, and runtime constraints $\Pi$ (permissions, retries, and budgets). The utility of a model–harness pair on task distribution $D$ is
$$
U(\mathcal{M},H)=\mathbb{E}_{x\sim D}\left[\,R(\tau_H(x))-\lambda C(\tau_H(x))\,\right],
$$
where $R$ is task reward, $C$ is normalized cost, and $\lambda$ controls the cost–quality trade-off. The *harness gain* is
$$
G_H(\mathcal{M})=U(\mathcal{M},H)-U(\mathcal{M},H_0),
$$
with $H_0$ a no-tools, single-turn baseline. This quantity is intentionally agnostic to whether a gain comes from better context selection, better tools, or better stopping decisions.

## Context compilation

The context compiler maps a growing trajectory to a bounded working set. It may summarize old observations, retrieve repository-local documentation, or inject a task-specific rubric. Retrieval-augmented generation provides a useful precedent for this separation between parametric knowledge and external context (Lewis et al. 2020). In practice, compilation is also where token budgets become an engineering decision rather than a model property.

## Tools and permissions

Tools expose actions with typed schemas: read a file, run a test, issue a database query, or navigate a page. Tool descriptions act as an interface contract (Yang et al. 2024), while permissions in $\Pi$ define the admissible action set. Tool-use research has shown that language models can learn when and how to call APIs (Schick et al. 2023); a harness adds the runtime checks that make those calls observable and interruptible.

## State and memory

State is the difference between remembering a plan and merely repeating it. We distinguish ephemeral scratch state, durable task memory, and an append-only trace for audit. The trace is valuable even when it is never shown to the model: it lets the verifier attribute a failure to a bad action, a stale observation, or an invalid assumption.

## Verification and recovery

A verifier turns progress into a signal. It can run unit tests, compare a page against a target, or ask a second model to critique an intermediate result. Reflexion-style methods use verbal feedback to improve subsequent attempts (Shinn et al. 2023); harnesses generalize the idea to any executable check. Recovery policies then choose among retrying the same tool, revising the plan, shrinking scope, or escalating to a human.

# Experimental Setup

## Tasks

We construct three task families that stress different parts of the loop: repository edits patterned after SWE-bench (Jimenez et al. 2024), browser workflows patterned after WebArena (Zhou et al. 2024), and structured API tasks patterned after $\tau$-bench (Yao et al. 2025). Each instance has a binary success criterion and a token-and-tool cost. To keep the comparison focused, every condition uses the same frozen 70B instruction-tuned model at temperature 0.2.

## Conditions

We enable five cumulative harness stages over single-turn prompting (Base), spanning six mechanisms: structured planning (Plan), typed tools (Tools), working memory (Memory), executable verification (Verify), and recovery governed by a bounded retry-and-budget policy (Full). ## Metrics

We report task success, normalized cost (model tokens plus tool latency), and recovery rate: the fraction of trajectories failing before verification that are repaired within the retry budget. Confidence intervals are omitted because the values are illustrative; the protocol is specified so that practitioners can reproduce the ablation with a live runtime.

Typed tools produce the largest single jump on API tasks (+19.8 points), while verification and recovery matter most on repository edits (+23.1 points over Memory), where a plausible patch differs from a passing patch. ## The cost of being capable

Capability is not free. Per attempt, Full incurs $1.90\times$ the normalized cost of Base ($1.58\times$ in model tokens plus $0.32\times$ in tool latency, averaging 6.4 tool calls per solved task). Yet expected cost *per successful task* falls by 41% because $3.2\times$ as many attempts reach a verified solution rather than an unrecoverable error. Table 2 also shows that removing budget limits raises cost by $1.37\times$ over Full while hurting accuracy via runaway retries: a bounded trajectory is cheaper per solved task than a short wrong answer.

# Discussion

## Why the harness multiplies capability

The model supplies general-purpose heuristics; the harness supplies opportunities to apply them repeatedly. Three mechanisms explain most of the gain:

1.  **Information gain.** Retrieval and observation expose facts that were not in the initial prompt.

2.  **Actionability.** Typed tools and agent–computer interfaces make intermediate decisions testable in the environment (Yang et al. 2024).

3.  **Error correction.** Verifiers convert silent mistakes into observations that redirect subsequent steps.

These mechanisms unify the decomposition and reflection patterns reported in recent agent work (Yao et al. 2023; Wang et al. 2025). The harness is therefore a policy over policies: it decides which context the actor sees, which actions are admissible, and when a trajectory is good enough.

## A control-theoretic view

Under partial observability, the harness maintains a belief state $b_t$ over task progress. A simple scheduler is
$$
b_{t+1}=F(b_t,a_t,o_{t+1}),\qquad a_t=\arg\max_{a\in A(b_t)} Q(b_t,a),
$$
where $A(b_t)$ is filtered by permissions and budgets in $\Pi$, and the actor approximates $Q$ through language generation. This view clarifies why stopping is a systems-level control decision rather than a formatting choice.

## Failure modes

A harness can amplify the wrong behavior. Prompt injection can poison retrieved context; a permissive router can turn a hallucination into a destructive action; and an overconfident verifier can certify a broken artifact. Long traces also create an observability paradox: more logs aid post-hoc diagnosis yet crowd out the working evidence needed for the next decision. Robust systems should therefore log everything, surface context selectively, and fail closed when checks disagree.

# Related Work

Our framing connects several lines of research. Transformers established the dominant neural sequence backbone (Vaswani et al. 2017); scaling studies showed that capability can emerge with model size and data (Brown et al. 2020; Wei et al. 2022). ReAct interleaves reasoning and acting (Yao et al. 2023), Toolformer learns API invocation (Schick et al. 2023), and Reflexion adds verbal feedback across attempts (Shinn et al. 2023). Retrieval-augmented generation separates external memory from parameters (Lewis et al. 2020). Recent interactive benchmarks and open agent runtimes make the systems and interface layer directly measurable (Jimenez et al. 2024; Zhou et al. 2024; Yang et al. 2024; Wang et al. 2025; Yao et al. 2025). We contribute a compact formalism for these pieces and an explicit metric for their joint effect.

# Limitations and Responsible Use

The numerical study is intentionally simulated to isolate architectural interactions and should not be read as a benchmark claim about any specific commercial deployment. Empirical evaluations must report task sampling, seed variance, tool timeouts, and human escalation rates. Harnesses also expand the security boundary: credentials, filesystem access, and browser sessions require least-privilege policies and auditable traces. We recommend publishing harness specifications alongside model weights so that evaluations compare complete systems.

# Conclusion

A language model becomes an agent when a runtime gives it state, tools, feedback, and a reason to continue. The resulting capability is a property of the pair $(\mathcal{M},H)$, not of the weights alone. This perspective suggests a practical research program: benchmark harness mechanisms independently, standardize tool and verifier interfaces, and report expected cost per verified completion. The punchline remains the title. In agentic systems, the harness is not a footnote; it is where the loop lives.

# Reference Harness Pseudocode

The following pseudocode summarizes the runtime loop used in the illustrative study.

```text
state <- initialize(task)
for step <- 1, ..., K do
    context <- compile(task, state, budget)
    action <- model(context)
    if constraints.reject(action) then
        state.add(error("permission"))
        recovery.update(state)
        if recovery.exhausted() then return failure
        continue
    observation <- router.execute(action)
    state.add(observation)
    if verifier.pass(state) then return success
    recovery.update(state)
    if verifier.fail(state) then
        if recovery.exhausted() then return failure
end for
return failure
```

# A Harness Checklist

For reproducible agent experiments, we recommend reporting: the context compiler and truncation rule; tool schemas, permissions, and timeouts; state serialization and memory retention; verifier implementation and false-positive rate; retry and stopping policy; token, wall-clock, and external-action budgets; and traces of representative failures. These details are often more predictive of observed behavior than a one-line model name.
